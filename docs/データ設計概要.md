### 0. 設計規約
#### 1. スキーマ全体方針・正規化レベル
##### データ層
- 第3正規形を基本とし、マスタ／トランザクション／結果を明確に分離する。
- 1 テーブル＝1 概念を原則とし、役割の違う情報を同じテーブルに混在させない。
- よく JOIN される属性（テナー文字列など）は軽い冗長化を許容するが、意味が二重管理にならないようにする。
##### アプリ層
- 読み取り系は JOIN を極力固定パターンにし、複雑な ad-hoc JOIN をアプリ側で乱発しなくて済むようにする。
- 書き込み系は「どのテーブルがどのテーブルの子か（1:1, 1:N）」の関係を意識してトランザクション順序を決める。

#### 2. ID・主キー／外部キー・命名規則
##### データ層
- 主キーは TEXT の論理 ID（`*_id` / `*_code`）を基本とし、必要に応じて複合 PK を使う。
- 外部キー列名は参照先と同名に揃え、FK 制約を必ず付与する（SQLite の FK を有効化して使う前提）。
- ID は長期的に不変なコードとし、意味変更や再利用は禁止する。
##### アプリ層
- ID をハードコードせず、マスタから取得した ID を使ってロジック分岐や画面表示を行う。
- 外部システム ID は別カラム（`external_id` 等）として扱い、内部 ID と混同しない。
- API モデルや UI では ID に依存しすぎず、説明カラム（`name`, `description`）も同時に扱う。

#### 3. 日付・日時・タイムゾーンの扱い
##### データ層
- 日付は TEXT `YYYY-MM-DD`、UTC 時刻は TEXT `YYYY-MM-DDThh:mm:ss.sssZ` に統一し、型混在を避ける。
- 列名は `*_date`（日付）、`*_at`（時刻）、`as_of`（論理市場日）など一貫した命名にする。
- タイムゾーンはカレンダー定義のタイムゾーンのカラムに紐づくカラムに格納し、DB 側は変換ロジックを持たない。
##### アプリ層
- 日付計算（T+N、スポットラグ、Fixing 日）は必ずタイムゾーンとカレンダーを考慮したロジックをアプリ側で実装し、DB にロジックを埋め込まない。
- 日付比較・範囲検索は DB 側では文字列比較前提で行い、型キャストを避ける。
- ユーザ表示用のローカル時刻変換はアプリ側で行う。

#### 4. 数値型・通貨・単位・スケールの扱い
##### データ層
- 金利・ボラ・スプレッド等の比率は REAL 型で実数（1% = 0.01）として格納する。
- 金額は REAL 型＋通貨列（ccy FK）で表現し、単位は数値に埋め込まない。
- 方向（ロング／ショート）は符号よりも、基本はタグ列（direction, pay_rec 等）で管理し、一貫した意味を保つ。
##### アプリ層
- 画面やレポートでは単位変換（% 表示、bp 表示、千円単位など）をアプリ側で行う。
- measure ごとに単位定義をコードに明示する。

#### 5. コード値・列挙値・CHECK 制約とマスタ化方針
##### データ層
- 値が小さな有限集合で、スキーマに密接に結びつくもの（オプションのコール / プット, ヨーロピアン/アメリカン/バミューダン, 等）は CHECK 制約で列挙する。
- 組織運用で拡張／削除があり得るコード値（商品マスタ, 補間方法マスタ 等）はマスタテーブルで管理する。
- コード値は TEXT の短い文字列とし、意味はデータ設計ドキュメントに記載する。
##### アプリ層
- CHECK 対象の列挙値は、コード側でも enum／定数として定義し、文字列の直書きを避ける。
- マスタ化されたコード値は、起動時などにロードしてキャッシュし、プルダウン／バリデーションに利用する。
- 新しいコード値を追加した場合は、アプリ側の enum も同時に更新する運用とする。

#### 6. 通貨・カレンダー・日数計算など市場共通マスタの設計方針
##### データ層
- 通貨、日数計算、営業日調整、カレンダー、参照金利などを共通マスタとして定義する。
- これらには `enabled`, `valid_from`, `retired_at` を持たせ、通貨廃止やインデックス仕様変更を期間で表現する。
- カレンダーは カレンダー定義（メタ）＋ 休日集合（日付リスト）構成とし、他テーブルからは カレンダーID を参照させる。
##### アプリ層
- 金利計算・スケジュール生成・営業日判定では、必ずこれらマスタを参照し、ベタ書きルールを禁止する。
- 新インデックス・新通貨が追加されたとき、プライシングロジック側は インデックスID / 通貨 ベースで汎用的に動くようにしておく。

#### 7. マーケットデータ（スナップショット／時系列）の設計方針
##### データ層
- マーケットデータスナップショット管理テーブルをルートとし、スナップショットIDをキーに評価に使用する各種マーケットデータの断面を束ねる。
- スナップショットは「評価に必要な情報が一式そろった単位」とし、後から一部だけ更新するのではなく、新規スナップショットIDを原則とする。
- 時系列管理が必要になった場合は、スナップショット系とは別テーブルで設計する。
##### アプリ層
- 評価時にスナップショットIDを指定し、その ID にぶら下がるマーケットデータのセットを一括ロードする。
- スナップショットのバージョン差分や系譜管理はアプリ側で行い、必要なら親スナップショットID等を使って追跡する。
- マーケット取込バッチは、1 つのスナップショットIDに紐づくマーケットデータセットを完成させてからロックする。

#### 8. 取引（trade）ヘッダ／商品別サブテーブル構造の設計方針
##### データ層
- 取引の共通部分を管理するテーブルを共通ヘッダとし、商品固有条件は各商品ごとの取引テーブル（trade_商品名）で 1:1 管理する。
- 各商品の取引テーブルと共通ヘッダはを紐づけるトレードIDは PK＋FK（→取引共通ヘッダ.トレードID）とし、ON DELETE CASCADE を基本とする。
- 商品種別は取引共通ヘッダの商品カラムで区別し、商品マスタにより 商品カラム ↔ サブテーブル名の対応を管理する。
##### アプリ層
- 新商品追加時は、新サブテーブル＋プライサー＋商品マスタ の登録だけで対応できるように、評価エンジンを商品中心で設計する。
- ライフサイクルの変更（取引の修正・キャンセル等）は取引共通ヘッダのステータスカラム等で制御し、サブテーブルの行は変更せず新しい取引を追加する（その際に親トレードIDに元のトレードIDをセットする）方針とする。

#### 9. プライシング設定（カーブ定義・参照金利ルール・モデルパラメータ）の設計方針
##### データ層
- カーブは定義とデータを分けて管理する。
- 参照金利仕様は1つのテーブルに集約し、インデックスごとに日数計算・Fixing ルール・O/N 期間化等を定義する。
- モデルパラメータは1つのテーブルに集約し、複数バージョンを管理できるようにする。
##### アプリ層
- プライサーは、通貨／インデックス／プロダクトから各データに紐づくIDを解決するロジックを持ち、DB 側には「設定値の保存」のみを任せる。
- 補間・外挿等のアルゴリズムはアプリ側で実装し、DBから取得したタグに応じてロジックを切り替える。
- モデルパラメータは 評価処理実行前に一括ロードしてキャッシュし、評価中に DB を何度も引きに行かない。

#### 10. シナリオ／ショックの設計方針　　　　　
##### データ層
- 個別のシナリオの定義とシナリオセットの定義をテーブルを分けて管理する。
- シナリオのショックについてはショックタイプ（幅か率か）を定義する。
##### アプリ層
- 評価処理実行時はシナリオセットを指定し、配下の個別シナリオを読み込んでマーケット・モデルに対するショックを適用する。
- ショック適用ロジックは対象のマーケットデータカテゴリ、オブジェクト、ショックタイプに基づく汎用関数として実装し、商品ごとに別実装を作らない。
- シナリオ管理 UI ではシナリオセット定義と個別シナリオ定義を編集できるようにし、コード変更なくシナリオ内容を変更可能にする。

#### 11. 評価実行管理と評価結果の設計方針
##### データ層
- 評価実行管理は実行IDを PK とし、基準日, マーケットデータスナップショットID, シナリオセットID などのカラム を保持する。
- 評価実行管理 / 評価結果 は append-only を原則とし、更新・削除は行わない。
- 日次PL、感応度、シミュレーション（ストレステスト等の自由なシナリオ）のそれぞれの計算結果はテーブルを分ける。
- 評価実行管理は各計算結果ごとに分けない。
##### アプリ層
- 評価開始時に 評価実行管理テーブル に 1 行 INSERT し、その 実行ID を全ての 評価結果 行に紐づける。
- 再計算やバージョン比較は、別 実行ID で結果を並存させ、差分計算はアプリ側で行う。

#### 12. 状態管理・フラグと論理削除方針
##### データ層
- マスタ系には 有効無効フラグ を持たせ、論理無効化で廃止・非推奨を表現する。
- スナップショットには ロック状態カラム を持たせ、ロック後は更新されない前提で設計する。
- 取引には ステータス（例：'NEW','AMENDED','CANCELED' 等）と アクティブフラグ を持たせ、ライフサイクルと評価対象可否を区別する。
- 無効化の理由や変更履歴はメモやコメント用のカラム、または別テーブルで管理する。
##### アプリ層
- 通常のクエリは 有効, アクティブ, ロック済 等を条件に含め、無効データを排除する。
- 更新・削除 API は状態フラグを必ずチェックし、ロック済み・無効化済みデータの変更を禁止する。

#### 13. 履歴管理・バージョン管理・有効期間（valid_from／retired_at 等）の扱い
##### データ層
- 履歴が必要なマスタには valid_from, retired_at を持たせ、「上書きではなく新行追加」でバージョン管理する。
- 取引のリプレイスは バージョン, 親トレードID 等で表現し、過去バージョンも保持する。
- 有効期間でフィルタしやすいよう、キー＋期間列にインデックスを付与する。
##### アプリ層
- 評価時は 評価基準日 と有効期間を突き合わせて、マスタの「その時点で有効なバージョン」を解決する。
- 取引履歴画面では 親 / 置き換え のチェーンを辿ってバージョン遷移を表示する。
- ユースケースに応じて「最新のみ」API と「履歴含む」API を分ける。

#### 14. 監査性・トレーサビリティ・再現性確保の方針
##### データ層
- 基本的にすべてのテーブルに created_at (DEFAULT NOW) を持たせる。（ただし、評価結果テーブルには持たせず、必要な場合は評価実行管理のcreated_atを参照する。）
- 評価実行管理テーブル に マーケットスナップショットID, シナリオセットID, 実行者 を持たせ、「どの条件で評価したか」を一意に再現できるようにする。
- 必要に応じてマーケットスナップショットに データハッシュ などを持たせ、入力セットの同一性を検証できるようにする。
##### アプリ層
- 評価や登録の操作ログは、アプリログとして別途出力し、DB に保存された ID と紐づけて追跡可能にする。
- 再計算ツールは 実行ID または 評価基準日, マーケットスナップショットID, シナリオセットID から条件を復元し、同じ条件で再実行できるようにする。
- 本番評価は必ず QA 済みのマーケット／シナリオのみを使うようにし、その条件を 評価実行管理 に残す。

#### 15. 制約（NOT NULL／UNIQUE／CHECK）と参照整合性・トランザクションの方針
##### データ層
- NOT NULL は「業務上必須」の列に積極的に付与し、NULL は「本当に未定義があり得る」列にのみ許容する。
- UNIQUE は論理的に一意な列に必ず付ける。
- CHECK 制約を用いて、列挙値や範囲を DB 上で保証する。
- FK 制約は原則すべて有効化し、孤児レコードを防ぐ。
##### アプリ層
- 画面・API の入力チェックは DB 制約を前提にしつつ、ユーザに分かりやすいエラーメッセージを返すための前段バリデーションとして実装する。
- INSERT／UPDATE はトランザクションでまとめ、途中エラー時はロールバックする。
- 取引登録は「マスタ存在確認 → 取引共通ヘッダ → 商品ごとのサブテーブル」の順序で処理する。

#### 16. パフォーマンス・インデックス設計・データボリューム想定
##### データ層
- 各テーブルに対し、想定件数と主なアクセスパターンを決めておき、それに基づいてインデックス数を決める。
- PK／主要 FK／主要フィルタ列（基準日, マーケットスナップショットID, 実行ID, トレードID など）にはインデックスを付与する。
- 大規模になりうるテーブル（実行結果, マーケットデータを格納するテーブル）では、必要最小限のインデックスに抑える。
- パフォーマンスとメンテナンス性のバランスとしてはデータが煩雑にならない程度にパフォーマンスを重視する。
##### アプリ層
- 大量の INSERT／UPDATE はバルク処理＋トランザクションで行い、1 行ずつコミットしない。
- クエリは必要な列のみ SELECT し、SELECT * を避ける。
- 重い集計やシナリオループはアプリ側メモリ上で実行し、「一気に書き出す」スタイルを基本とする。

#### 17. 拡張性・後方互換性・スキーマ変更の基本方針
##### データ層
- 既存列の意味変更・削除は避け、新要件は列追加／マスタ行追加で吸収する。
- ENUM／CHECK の値集合は追加のみ許容し、既存値の意味を変えない。
- 非互換な変更が必要な場合は、新テーブルを定義し、旧テーブルから移行する。
##### アプリ層
- 新しい列は「存在すれば使う／なければデフォルト」のように扱えるようにし、旧バージョンの DB でもアプリが落ちない構造にする。
- 将来の GPU／並列処理等の導入を見据え、スキーマはできるだけ「バルク処理しやすい形」に保つ。

#### 18. ネーミング規則・表記ルール・コメント／ドキュメント化方針
##### データ層
- テーブル名・カラム名は小文字スネークケースで統一する。
- カラム名は役割が分かるように接尾辞を揃える（*_id, *_date, *_rate, *_flag など）。
- データ設計ドキュメントには必ず「概要／使用目的／項目一覧」を記載し、DB スキーマと同期させる。
##### アプリ層
- エンティティクラス名はテーブルと対応させつつ、言語の慣習（PascalCase 等）に従う。
- SQL はリポジトリ層等に集約し、クエリ定義の重複を避ける。

#### 19. データ品質管理・QA 状態・検証ルール
##### データ層
- マーケット系・スナップショット系には品質状態を持たせる（例：'RAW','CHECKED','APPROVED'）。
- 取込ログ・エラー情報を格納するための専用テーブル（必要なら）を用意し、集計しやすい形にする。
- QA に関する閾値設定やルールは、マスタ化可能なものはテーブルで表現する。
##### アプリ層
- QA 状態が一定以上のデータのみを評価で使用し、RAW データは原則評価から除外する。
- マーケット取込後や評価前に QA チェックを行い、閾値超過・不整合はログ＋画面・レポートで通知する。
- QA ルールはコードに埋め込まず、可能なものはマスタから読み込む形にし、調整を容易にする。

#### 20. セキュリティ・アクセス制御・環境分離（本番／検証／開発）の方針
##### データ層
- 環境は本番環境のみ。
- 機密度の高い情報を扱うテーブルが出てきた場合は、論理的・物理的に分離できる構造にしておく。
- DB ユーザ権限は「読み取り専用」「読み書き」など最低限のロールに分ける。
##### アプリ層
- 認証・認可はアプリ層で実装し、ユーザのロールに応じて参照可能な機能・データを制御する。
- 接続先 DB は環境変数などで管理する。（本番環境のみだが、実践的な実装としてそのようにする）
